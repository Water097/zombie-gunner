# 17 · 技能表现设计要点（形态 / 动画 / 受击）

> **范围**：只谈「看得见的部分」。**不谈数值**（伤害、冷却、倍率、成长曲线见 02 / 03 / 11 册）。
> **来源**：2026-11-02 ~ 11-12 从概念图 → Demo 实装 → 技能实验室，中间反复返工的记录。02 册 §2.6/§2.7 是理论源头，本文是落地后补上的「踩坑版」。
> **定位**：做下一个技能、或改任一技能表现之前，先过一遍 §五 检查清单。

---

## 零、一条元规则

> **技能是「事件」，不是「图标」。**（02 册 §2.6）
> 图标告诉玩家「这是什么系」，事件才告诉玩家「它干了什么」。第一版概念图做了 9 个只有颜色不同的元素球，被推翻就是这个原因。

这十几轮返工，几乎全部可以归到元规则派生出的三条判据上：

| 判据 | 含义 | 违反时的典型症状 |
|---|---|---|
| **所见即所受** | 判定用的几何量，渲染必须读同一个字段 | 火区看着是椭圆、判定是正圆；扇面画得比判定宽 |
| **所见即所处** | 演出进度必须来自实体真实状态，不能自己编时间 | 弹体没飞到敌人就掉血；闪电挂在那儿不动；枪口无目标乱摆 |
| **单看好看 ≠ 放一起好看** | 判据是「一眼能不能说出场上正在发生哪几件事」 | 六技能全开时某个技能被完全遮住；两条竖线并成一条 |

**这三条不是美学偏好，是信息传达的正确性要求。** 用户反馈里最尖锐的几次（"这符合物理定律吗"、"怎么直接穿透了"、"我看到的所有技能受击效果都一样"）本质都是这三条被破坏。

## 一、形态层 · 造型语言与识别性

### 1.1 形态 = 机制说明书

每个技能先定**空间占位**，再定造型。9 个技能必须占不同的位，否则玩家分不清谁在干什么：

| 占位 | 技能 | 造型要读出来的事 |
|---|---|---|
| 点 → 圆（落点） | 温压弹 | 弹道笔直、接触即爆、单段 |
| 点 → 小圆 | 干冰弹 | 全程无火、冷调压到底 |
| 精准单点（空降） | 电磁天雷 | 快、准、只打一个点；**不做**大范围地环，否则读成 AOE |
| 实体（纵向） | 装甲车 | 是装甲车不是坦克：方盒 + 履带 + 迷彩 + 黄色识别标，无炮塔长炮管 |
| 线（持续） | 高能射线 | 发生器 + 脉冲（脉冲 = 多段的可视化） |
| 面（扇面） | 制导激光 | 会动的「面」，与「一根线」明确分开 |
| 实体（定点） | 哨戒机 | 「它自己会打」这件事看得见 |
| 面（区域） | 燃烧地带 | 起燃 / 扩散 / 持续 / 慢慢熄灭，四段都要看见 |
| 实体（横向） | 旋转刀轮 | 画面上是「横着扫过去」 |

### 1.2 参考图对齐：图标装饰 ≠ 实体结构

**这是返工次数最多的一条。** 图标是静态构图，允许在主体旁边摆装饰；游戏里主体在飞，装饰跟着飞就违反物理直觉。

- 干冰弹旁的**六角雪花**、冷雾点 → 删。只留弹体自身结构 + 两侧尾翼。
- 温压弹的**两侧漂浮火焰三角** → 删。
- 温压弹的**红色圆球头** → 改 ogive 圆弧锥子弹头。
- 弹体上的**菱形冰块** / **木块加三角箭头** / **头比尾巴大** → 全部废弃。

> 结论：**只画「长在弹体上的东西」**。判断方法很简单——把这个元素固定在弹体上，它会不会随弹体一起移动/旋转？会，就是结构；不会，就是背景装饰，别搬。

### 1.3 导弹造型规范（已定稿）

圆柱弹体四层明暗（左受光 / 右压暗 / 中央高光 / 识别环带）+ 子弹头 ogive 圆弧锥 + 后部小尾翼（温压只露出一点点）+ 尾喷口 + 向后喷的尾焰。温压 = 深灰钢 + 橙红弹头；干冰 = 冰蓝 + 白尖锥弹头 + 两侧三角翼。

### 1.4 3/4 俯视的统一透视语言

摄像机不是全俯视也不是正侧视，屏幕 y 同时承载「高度」和「纵深」，只有一条地面线、没有地平线，越靠上 = 越远。

- **地面元素一律压扁成椭圆**（`ry ≈ rx × 0.34`，`GROUND_K`）。火区、电环、焦土都遵守，视觉与判定同源。
- **垂直起飞的东西**（弹道 / 雷 / 光束）沿屏幕 y 轴向上，**不倾斜**。
- **立体物件**（装甲车 / 炮台）顶面占大部分面积，底部露一条前脸或尾板，才读得出 3/4 体积。
- 环形按列求行绘制，按角度采样会在扁椭圆两端断成虚线。

### 1.5 配色与光效纪律

1. 一个技能**只用一个主色系 + 白核**（白核 = 能量密度峰值，不滥用）。
2. 硬形体 a=1；半透明只用真 blend（`p.disc`），**不要用低 alpha 的 `p.rect`/`poly`**（走 Bayer 网点会出棋盘格）。
3. 光效只加色（`glow` / `glowLine` / `light`），不用 alpha 填充。
4. **闪电 / 电弧不许出现白色线段**：`glowLine(起点→终点)`、amp 过小的 `arc()`、白色折线内芯都会被读成「一根白线 / 激光」。全部改逐段折线辉光 `boltGlow`，描边用电紫色阶；白色只允许出现在落点小核或端点闪点（**点，不是线**）。

### 1.6 剪影恒定，配色随品级换

`tiers.mjs` 六档色板（白 / 蓝 / 紫 / 粉 / 金 / 赤红+黑纹）：**剪影一行不改，只换色阶与光效预算**。品级的视觉是「一套函数」，不是「型号数 × 品级数」张图。玩家靠剪影认出是同一把枪 / 同一件甲，靠配色认出档位。概念图预览页做成切换 tab，切档整套换装。

### 1.7 形态候选让用户拍板

哨戒机形态弱，没有擅自重做，而是出了 4 个可视化候选（双管机炮塔 / 浮空无人机 / 棱镜激光塔 / 重炮炮台）让用户选，选定后才落地。**主观审美由人拍板，AI 只负责把选项做到可比较。**

### 1.8 唯一实现原则

定稿的 `drawDroneBase` / `drawDroneHead` 是唯一实现，Demo 实机、技能实验室、候选页全部 import 它；燃烧地带的 `flame-field.mjs` 同理，概念图与 Demo 只调同一份函数。**不搞第二套画法** —— 两套实现必然漂移，漂移就会制造「所见非所受」。

## 二、动画层 · 时间、坐标与时序

### 2.1 统一四拍

`出手 → 飞行/展开 → 命中 → 残留`。每一拍都要能把机制读出来。四拍不是流程装饰，是玩家理解技能的时间骨架；燃烧地带的「起/扩/烧/灭」、闪电的「积云/劈下/命中/消失」都是它的具体化。

### 2.2 坐标系只有一个真相源

- **渲染层角度 = 内核 atan2 角**（0=+x、π/2=+y，`dx=cos, dy=sin`）。
- 概念图 `skills.mjs` 的扇面用「0=正上」的 `x=sin, y=-cos`，那是**画廊自己的坐标系**。整块搬进 Demo 会差 90° —— 制导激光「往底部扫而不是往敌人方向扫」的根因就在这里。
- 判定用的几何量（扇面半角 / 火区椭圆 / 车身尺寸 / 刀轮半径）渲染必须读**同一个字段**。

### 2.3 朝向：局部 -y 是弹头 / 枪口

要把它对到标准 atan2 角 `ang`，必须 `rotate(ang + π/2)`；只 `rotate(ang)` 会让弹体横过来。枪口方向**只能由目标决定**（`turretShots.tx/ty` 或最近敌人），不许用 `sin(time)` 摆动。同理，装甲车 `vy<0` 是向上碾，车头识别标在行进方向，别加多余的 `rotate(π)`。

### 2.4 时钟：实例时间，不是全局时间

演出进度一律用实例 `1 - life/maxLife` 归一化。用全局 `world.time` 的后果：光束每隔几秒周期性熄灭、炮台自己摆来摆去、所有同类技能同步闪。**开火相位也要由真实事件驱动**（把 `shot.life` 映射成充能/光束进度），不要自己编循环。

### 2.5 时序演出 ≠ 静图渐隐

闪电/爆炸是一段「闪现 → 命中 → 消失」的时序，不是一张挂在那儿渐隐的静图。**折线 seed 必须逐帧变化才会「闪」**（用户："电磁天雷为啥闪电不动"）。

「快」是设计意图，不是省事的借口：实机几百毫秒就是快，实验室把 `maxLife` 拉长即可逐拍看清，**同一份渲染代码不用改**。这也是实验室存在的理由之一。

### 2.6 运动部件：哪些该动、哪些不该动

- 装甲车：只有履带在滚，车身不动。
- 无人机：`base`（地面影 / 推进光 / 能量翼）不随枪口转；`head`（环体 / 独眼 / 炮口 / 光束）才 `rotate(aim + π/2)`。
- 枪口：只沿目标方向，动作只允许沿枪管方向（后坐 / 枪口焰）。

### 2.7 基础技能 ≠ 节点卡效果

「那条白线」改了三轮颜色都没解决，最后发现根因不是颜色：**实验室把 15 级「弹射电弧」和 20 级「雷暴区」两个节点卡效果混进了基础电磁天雷**，横线是弹射电弧、虚线大圆是雷暴区。现在基础天雷只造一道落雷。

> 教训：排查「多出来的东西」，先问**它该不该存在于这个层级**，而不是先调它的颜色。

### 2.8 图层顺序与遮挡

火场在敌人下（地面），光束 / 落雷 / 弹体在上。地面火对比度过会吞掉敌人剪影，敌人需要额外描边或亮点边缘，否则「场上有几只」读不出来。

### 2.9 性能预算属于表现设计

每只敌人每帧跑整条 pixelfx 管线 → 怪多时 FPS 掉到 10。改成**按敌人类型预烘焙动画帧序列**（一次性 pixelfx 渲染），运行时只 `drawImage`，每敌随机相位偏移避免整齐划一，死亡后 `reap()` 回收。**表现方案必须在目标同屏数量下验过帧预算**，否则再好看也不可交付。

## 三、受击层 · 时机、结算与专属反馈

### 3.1 命中时机由实体上报事件

**绝不用固定时间比例硬触发。** 每个技能在自己的 `tick` 里按弹体真实位置 / 落雷进度 / 刀轮位置 / 火区周期上报 `w.events.push({ kind })`，舞台消费后画受击层。用固定比例的直接后果就是「干冰弹都没飞到敌人那儿，敌人就受到攻击了」。

### 3.2 命中后实体要正确结算

温压弹命中即爆、**弹体消失不穿透**（用户："怎么直接穿透了"）。命中不只是「掉血」这个数字事件，它同时是「这个实体生命周期结束 / 转换成另一种表现」的事件。

### 3.3 每个技能的受击效果必须不同

| 技能 | 专属受击表现 |
|---|---|
| 干冰弹 | ❄ 冰晶包裹、蓝色冰棱 |
| 温压弹 | ✹ 爆燃、扩散冲击环 + 碎屑 + 火苗 |
| 电磁天雷 | ⚡ 麻痹、电弧在身上爬 |
| 燃烧地带 | ♨ 持续灼烧火苗（每跳一次） |
| 装甲车 | ▣ 击退、压扁并位移 |
| 高能射线 | ⌁ 青色脉冲环（逐段） |
| 制导激光 / 旋转刀轮 | 横向切痕 |
| 哨戒机 / 主武器 | 弹击火花 |

状态名、飘字颜色、闪光颜色、底部统计都随技能变。**共用一套白闪 = 玩家无法从反馈里读出发生了什么**（用户："我看了所有的技能的受击效果都是一样的"）。

### 3.4 与状态系统对齐

7 种状态 + 硬门禁（冻结 → 装甲尸车 ×3）。受击视觉要能读出**施加了什么状态**，而不只是「掉了一格血」。状态施加只走 `apply`，伤害只走 `dealDamage`（飘字标注、门禁、DoT 都在这一处）—— 结算入口统一，视觉才不会和逻辑分家。

### 3.5 可见性有阈值

原实现 `hitFlash` 只有很短一段 + 2px 低透明度白色描边，实测「基本看不见」。改成加色**填充闪白 + 白环**，并覆盖精灵与几何占位两条渲染路径。**"做了"和"看得见"是两件事**，反馈强度要按实际画面尺寸和同屏噪声来定，不能按代码里有没有这一行来定。

### 3.6 多通道反馈

闪白 + 抖动 + 血条 + 伤害飘字 + 命中火花 + 底部累计统计。多通道不是堆特效，是让不同信息走不同通道：状态走颜色，量走飘字，趋势走血条，累计走统计。

## 四、你没点名、但整个过程一直在处理的（补充）

### A. 同屏叠加可读性（02 册 §2.7）

专门做了 4 张叠加测试图，判据只有一条：**一眼能不能说出场上正在发生哪几件事**。四条结论：

1. 温压弹爆炸**视觉**尺寸过大会盖住整个战场 → 缩视觉尺寸（不是玩法半径）。
2. **竖直类技能必须分车道**：高能射线 + 电磁天雷都在中间会并成一条竖线 → 固定左/右分列。
3. **同屏上限约 4~5 个**：6 个全开时哨戒机被刀轮和光束完全遮住 → 「一局 4 槽」是对的，超过 5 个要做演出降级。
4. 地面火会吞敌人剪影 → 敌人需要额外描边。

> ⚠️ 2 / 3 目前在**概念图层面测出结论，Demo 尚未落地**。

### B. 验证与观测设施本身是设计工具

技能实验室不是"附带的测试页"，它决定了形态问题能不能被看见：单技能大舞台 / 九宫格同屏 / 暂停 / 重播 / 调速 / 自动循环 / CD 条 / **目标方向轴**（制导激光的坐标系 bug 就是靠它暴露的）/ 弹体特写放大 / 主舞台放大。另有武器实验室（弹匣 → 开火 → 打空 → 换弹状态机）。

**测技能不靠抽卡、不等 CD、不被怪物干扰** —— 否则一次验证要等太久，形态问题就会被放过。

### C. 参数中心单一真相源

`tuning.mjs` 作唯一默认值来源，schema 驱动 UI、localStorage 持久化；实验室参数**不写回实机**；控件上诚实标注「亮色 = 影响演出，暗色 = 仅数值结算」，不假装能看见伤害。

### D. 效果开关

`fx` 四类开关（敌人发光 / 死亡效果 / 粒子 / 飘字）。既能做 A/B 对比，也能快速定位是某个效果层拖了性能或挡了视线。

### E. 引擎无关分层

`status/*`、`combat-core`、`cards` 不依赖 DOM，Node 可测；**渲染层只画不判断**。这条架构纪律直接决定了「判定几何」和「视觉几何」能共用同一个字段，是「所见即所受」的前提。

### F. 验证方法本身要能证伪"画了个空"

单测只是底线。表现层靠：无头 Canvas2D 桩（不抛异常）+ **绘制调用计数**（防止某个技能画出来是空的）+ 方向 / 坐标 / 最长线段**硬断言** + DOM 桩跑真实交互路径 + 像素级组合验证（品级 72 组合互不相同）。

> 反复出现的教训：**断言失败时先怀疑验证脚本，别急着改业务代码**（这轮里至少 3 次是桩脚本的采样方式没覆盖 `ellipse` / `fillRect`）。

### G. 纪律沉淀机制

每轮踩坑立刻写进 `docs/16` §七 的纪律清单，防止重犯；记忆镜像 `memory/` 随 git 走（改完跑 `memory-sync.mjs`）。**没有这层沉淀，同一类错误会隔几轮换个形态再来一次** —— 白线问题返工三轮就是例子。

### H. 画布与展示尺寸

舞台尺寸、DPR 上限、放大模式（参数面板移到下方仍可用）、画布缩放不能盖住 HUD（配置工作台常驻左栏后画布整体右移避让）。表现设计包含「在什么尺寸下看」，看不清等于没做。

## 五、检查清单（做新技能 / 改表现前逐条过）

- [ ] **空间占位**和已有 9 技能不重复，剪影能一眼分辨
- [ ] 造型只含「长在实体上的结构」，没有从图标搬来的漂浮装饰
- [ ] 四拍齐全（出手 / 飞行展开 / 命中 / 残留），每拍能读出机制
- [ ] 判定几何与视觉几何读同一个字段（火区椭圆、扇面半角、车身尺寸…）
- [ ] 角度用内核 atan2 系；局部 -y 用 `rotate(ang + π/2)` 对上
- [ ] 时钟用实例 `life/maxLife`；动态折线 seed 逐帧变化
- [ ] 枪口 / 弹头方向只由目标决定，不随全局时间摆动
- [ ] 基础演出里没有混入节点卡 / 质变卡的效果
- [ ] 没有贯穿长直线（白色尤其），闪电一律逐段折线
- [ ] 命中由实体事件上报，不是固定时间比例
- [ ] 命中后弹体正确结算（爆掉 / 消失 / 穿透，符合机制）
- [ ] 受击表现**与本技能状态**对应，且与其他技能不重样
